Every tip has to answer one question again and again. What runs next? How are computations orchestrated? A CPU answers that question one way. A GPU answers it another way. A dataflow style accelerators tries to move the decision into the compute graph itself. Same math. Very different ways of deciding when the math runs. First, let us be precise about this comparison. A modern server CPU is general purpose. It is built for handling branches, operating system work, databases, Python and many different kinds of code. A GPU is also programable, but it is optimized for throughput. Running the same kernel across many pieces of data at the same time. A dataflow style AI accelerator is also programable, but it handles a small but useful subset of compute patterns very efficiently, like AI models. So this is not about CPU bad versus accelerator good. It is about where the scheduling decision actually looks. Before going further, here is the design tradeoff underneath all of this. ACPU has a handful of powerful cores that is optimized for latency. So it is built to take an instruction stream and push through the instruction stream as fast as possible. That is a latency design. A GPU has thousands of simpler cores. Now, any given core is weaker than a CPU core,  but there are so many of them that the chip can do simple math on huge amounts of data at once, and that is a throughput design. Same transistor budget, but spent in two very different ways. We will use a tiny workload so that the difference is easy to see. First add x, which is a plus b, and then produce the result y my by multiplying x with c. The arithmetic is boring on purpose. The interesting part is where the decision lives, which operation, and how each operation is allowed to execute. That decision is in the heart of control flow versus dataflow. So let's start with the CPU. The software gives CPU an instruction stream. The stream defines the correct result of the program. A modern out of order CPU does not simply fetch one instruction,  execute it and then go to the next instruction. Inside the chip, instructions are broken into smaller micro operations. The CPU looks at a window of such operation and asks for which operations are the inputs actually ready? It may execute these instructions out of order independently, as long as their inputs are ready, but it still retires these instructions one by one so that the program behaves correctly. This is why CPUs feel comfortable for ordinary software. They are good at changing directions, branches, function calls, pointer-heavy code, small pieces of work that all do not look the same. The trade off is that CPU spends a lot of hardware area on control machinery. Prediction, scheduling, caching, keeping the illusion of program order. For very large regular tensor math that control machinery is useful, but it eats up a lot of the chip's real estate, which instead could be used to engage and improve the arithmetic throughput. Now let us move to the GPU. GPU is designed with many simple compute lanes instead of a few powerful ones. A GPU is still given an instruction stream, so nothing changes there, except the GPU's instructions stream. The scale is the difference. A single instruction stream controls the execution of many parallel compute lanes, each crunching a different data in parallel. The parallel compute streams are called threads, which are grouped into warps or waves of 32. Now going back to the tiny workload, a GPU runs an ad and a model on a vector of data elements, not on a single data element, thereby significantly improving the arithmetic throughput. Now, if you really have a single element on which you need to do an add and a mul, then a CPU versus GPU execution is no different. The GPU scheduler asks a different question from the CPU. Instead of looking for one ready instruction from a small instruction window, a streaming multiprocessor in a GPU looks for a ready warp or wave. If one group is waiting on memory, another group can be used to execute on the hardware. This is how GPU hides memory latency, not by making memory magically fast, but by keeping many groups continuously in flight. The throughput design is really paying off here. This is also why GPUs love regular work. If all lanes in the warp do the same kind of operation on different pieces of data, then the hardware stays busy. If lanes take different branches, then the warp has to handle those paths with masks and some of the lanes may be idle while the others are running. The code still executes correctly. The cost is that the compute utilization is lower. On a CPU or a GPU the compute engines are backed by a tiered memory hierarchy. Now this memory hierarchy is made up of caches or the main memory. The instruction stream given to the CPU or GPU. It only defines the computation sequence by pointing at memory, but by pointing at addresses in memory. The hardware then implicitly moves the data from the memory into the compute course so that the execution can happen. So the compute schedule lies with the instructions stream, but the data movement is implicit. Dataflow accelerators level the playing field by making data movement into a first class architecture concept. Both compute and data movement are explicitly scheduled. Dataflow accelerators are also programable. In fact, they have multiple instruction streams, some of them specifying compute and some of them specifying data movement. With this, complete compute patterns can be mapped and explicitly programed and oftentimes done automatically through a graph compiler. Dataflow accelerators unlock extreme efficiency when the application's compute patterns map well to the hardware's compute fabric. Now we will use this tiny example again. So lets consider a dataflow accelerators which has two compute engines. Both of which can talk to each other and is also connected to the memory. Now in this case add is mapped to one of the compute engines, and the model is mapped to the other compute engine. Now the first compute engine is explicitly instructed to receive data from memory, perform the add operation, and send the output to the second compute engine. The second compute engine does the mul and then writes the data back to the back to the memory. So this way both the compute and the data movement are explicitly programed and executed.  A systolic array is a great example of a dataflow accelerator. It is used in many AI accelerator, and it is at the heart of the compute horsepower of those accelerators. It is a 2D grid of compute engines, each connected to their neighbors. Weights and activations flow through a grid of multiply and accumulate units. Each unit does a small piece of the matrix multiply and passes the data to its neighbors. This can be extremely efficient for dense linear algebra, because data fetched by one compute engine is directly used by the other without really moving through the memory hierarchy. So in summary, a CPU may tolerate messy control flow but run out of arithmetic throughput. A GPU may have huge throughput, but lose efficiency if the work is too small, too branchy or badly laid out in memory. A dataflow style accelerator may be very efficient when the application has fixed compute patterns, and that can be mapped efficiently onto the underlying compute fabric. It can struggle when shapes, control flow or unsupported operation makes the compute patterns dynamic. The math did not change. was the same arithmetic. The scheduling problem changed different ways to answer what runs next.
